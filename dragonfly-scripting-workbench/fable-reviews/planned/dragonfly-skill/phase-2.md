# Phase 2 — write the `dragonfly-scripting` skill

Goal: a skill folder `dragonfly-scripting/` in this repo that an agent loads when it designs, reviews, optimizes or measures Lua (EVAL/EVALSHA) operations and key layouts on Dragonfly. Every rule in it is backed by Dragonfly evidence: `lab/RESULTS.md` (measured on v1.34.0) or a Dragonfly doc/source citation from `research/*.md`; a Redis-only source may explain Lua API semantics but never justifies a performance rule. Each rule carries an evidence tag: `[lab Qn]`, `[df-src path:function]`, `[df-doc URL]`; a rule with only a Redis tag is deleted or moved to the audit table as unverified.

## Decisions already taken (from lab Q5, `lab/RESULTS.md` Q5 verdict/mechanism paragraphs)
- The skill presents two regimes and tells the reader to determine which one they are in first: (a) default flags — a shared `{hashtag}` does not co-locate keys, every multi-key script is io-coordinated (~27 µs per `redis.call`, measured), so batching calls is the dominant win; (b) `--lock_on_hashtags` (or a single-key script) — shard-local, ~1 µs per call, batching matters less and the shard's CPU time is the limit. Detection: `INFO ALL` counters `eval_shardlocal_coordination_total` vs `eval_io_coordination_total` before/after one invocation, plus `dragonfly --helpfull`/`CONFIG GET lock_on_hashtags` if supported. `disable-atomicity` and `allow-undeclared-keys` are fast-path killers in regime (b).
- For the example workload (one hashtag for all keys, no `--lock_on_hashtags` in prod) the skill's recommendation order is: 1) measure the counters, 2) evaluate enabling `--lock_on_hashtags` (Q10 numbers), 3) batch reads/writes (Q2/Q7 numbers), 4) bound work (Q3), 5) keep big blobs off the hot path (Q4).

## Decisions taken on handoff-1 open items (`fable-reviews/planned/dragonfly-skill/handoff-1.md`)
1. The hmget variant's narrowed `record_missing` check is NOT contract-neutral in general. The skill recommends the contract-preserving rewrite: batch every read the original performs (metadata and existence checks for the whole window via chunked HMGET), keep whole-window protocol checks, and treat "bound payload reads to batch_size" as a separate contract decision the owner must make (Q3 isolates its value at 1.1–1.8x; the bulk of the Q7/Q10 win is batching). State this explicitly where claim_mailbox_batch is used as the example.
2. `--lock_on_hashtags` is presented as a measured trade-off with a decision rule, never as a default: it makes a one-hashtag multi-key script shard-local (26.95 → 1.54 µs/call, lab Q5 lock_on_hashtags row) but pins every key with that tag to one thread, so a workload with tag cardinality below the shard count serializes on one core and shows head-of-line blocking (Q11d: trivial EVALSHA 81 → 7712 µs under 4 loaders). Rule: consider it only if distinct tags ≥ shards or total script CPU time fits one core; measure both arms with the workload's real concurrency.
3. Quote ratios from Q10 (back-to-back arms) and absolutes from the standalone runs, as the Q10 reconciliation note says; never mix.
4. Numbers are quoted with their conditions (proactor_threads, flags, value size, N) in one clause; the reader must be able to tell a 1-key shard-local number from an 8-key io-coordinated one.
